# KinderCore — спецификация собственной аналитики лендинга

Статус: проектное решение от 29.10.2026. Не считать внедрённым до создания D1 binding, тестирования и проверки Production.

## Цели
- Понять, откуда приходят посетители и какие страницы/разделы/CTA им интересны.
- Оценивать качество контента и SEO в связке с данными поисковых кабинетов, не выдавая корреляцию за причинность.
- Собирать минимум данных, без профилирования и без персональных данных детей/родителей.

## Архитектура-кандидат
- Статический сайт Cloudflare Pages.
- Same-origin POST endpoint через Pages Functions: /api/analytics.
- Cloudflare D1 для хранения ограниченного набора событий и агрегатов, после проверки тарифных лимитов и создания binding вручную владельцем.
- Никаких Supabase, CRM, сторонних SDK, рекламных пикселей, cookies для аналитики или fingerprinting.

## События первой версии
1. page_view — только нормализованный pathname из списка существующих страниц/разделов, без query string.
2. cta_click — фиксированный идентификатор CTA, не произвольный текст/значение.
3. traffic_source — ограниченная категория источника и UTM-значения после ограничения длины и очистки; никогда не сохранять полный URL/referrer с query string.
4. device_class — только грубая категория mobile / desktop / tablet / unknown, без точного User-Agent.

Не собирать имена, email, телефон, форму ввода, полный IP, точный User-Agent, рекламные ID или устойчивый идентификатор пользователя. Не строить индивидуальные пути конкретного человека.

## Минимальные требования к endpoint
- Принимать только POST JSON same-origin; проверять Origin при наличии и Content-Type.
- Ограничивать тело запроса (например, 2 KB), число событий и длину каждой строки.
- Строгий allowlist event name и полей; неизвестные поля отвергать/игнорировать.
- Не доверять клиентским timestamp; серверное время выставлять на стороне функции.
- Не писать в БД raw IP/User-Agent; не логировать тело запроса в исключениях.
- Применять лимитирование/защиту от спама, не полагаясь только на Origin.
- Параметризованные SQL-запросы, минимальные привилегии и тесты.
- Ошибка аналитики не должна ломать загрузку сайта или основную навигацию.

## Хранение и отчёты
- Перед запуском определить и записать срок хранения сырых событий; начальный кандидат — 30 дней, но утвердить его после оценки необходимости и юридической проверки.
- Дольше хранить только агрегаты, если они действительно нужны; не делать повторную идентификацию.
- Внутренний отчёт: посещения по дням, источники, популярные страницы/разделы, клики CTA, простая конверсия. Не показывать персональные профили.

## SEO — не часть счётчика
Проверить отдельно: robots.txt, sitemap.xml, canonical после выбора домена, уникальные title/description, H1/H2, Open Graph, favicon, внутренние ссылки, HTTP status/indexability, structured data только на подтверждённых фактах, mobile usability, performance, доступность. После собственного домена — Яндекс Вебмастер и Google Search Console. Собственная аналитика сама по себе не поднимает позиции в выдаче.

## Блокеры до Production
- Подтвердить применимые условия Cloudflare Pages и D1, доступность и лимиты; вручную создать D1 database и binding в Pages.
- Проверить обработку технических метаданных Cloudflare Pages независимо от собственного счётчика.
- Определить правовое основание, сроки хранения, текст политики и необходимость уведомления Роскомнадзора до начала сбора.
- Написать тесты и проверить, что никакие IP/User-Agent не сохраняются.
- Не включать клиентский сбор до прохождения проверок и фактической проверки endpoint.
